# 100 improvements: making OnCo exhaustively useful

Written 2026-09-09 against the corpus at `npm run validate` = 3,948 entities in 18 kinds (64 cancers, 377 products, 92 targets, 348 technologies, 401 trials, 295 companies, 415 people, 1,107 ideas, 146 key papers) and roughly 8,000 static pages. Everything below is checked against `src/data/hub-ideas.ts` (all three waves), `docs/GAPS.md`, `src/lib/nav.ts`, `CHANGELOG.md` and the code: nothing here is already built or marked `shipped`. Where an item realises a `planned` or `proposed` hub idea, the row says so.

## How to read and execute this

- **Side data over schema changes.** Every new dataset is a keyed side file (`src/data/<thing>.ts`, the pattern of `payloads.ts`, `biomarkers.ts`, `regional-approvals.ts`, `trial-outcomes.ts`) validated against the graph at build time. No item requires a change to `src/lib/schema.ts`; promotion into the schema can follow later.
- **Shared files.** `src/lib/schema.ts`, `src/data/index.ts`, `src/components/EntityDetail.tsx`, `src/app/[kind]/page.tsx`, `src/lib/nav.ts`, `src/app/layout.tsx` and `package.json` are edited only by the main session after merge. Rows that need them say **wiring:** in the files column; the agent ships the component or data plus a standalone route so the work is testable before wiring. Every new route also needs a `nav.ts` entry, which is left implicit.
- **Batches.** Ten batches of ten. Each batch owns a disjoint set of files (listed under each heading) so ten agents can run in ten worktrees without touching each other's files. Batch letters are used in the `Batch` column.
- **Effort.** S = under a day for one agent, M = one to three days, L = a week or a sustained data effort.
